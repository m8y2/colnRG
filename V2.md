# Coln River Guardians — v2

v2 is a rebuild of the dashboard for people with no technical background, plus a reporting
engine that writes one report per round of testing.

**Live at `https://www.colnrg.app`, deployed 2026-09-17.** It was built and first deployed
alongside v1 at `/new`, keeping v1 at `/`; the owner then asked for v2 to be the main site and
v1 retired. v1's code and database are untouched, on disk on the droplet and on the `main`
branch, just not what nginx points `/` at any more -- see "Deploying" below for where.

Everything here is on the `v2` branch.

## Why v2 exists

Two problems with v1:

1. **It was written for someone who already understood it.** "Phosphate 0.17 mg/L, WFD
   Moderate" means nothing to a volunteer, a parish councillor or a schoolchild.
2. **The reporting was a thin beta** — one prompt producing a wall of prose, with nothing
   stopping the model inventing figures.

Two more problems were found while building it, and they were the bigger ones:

3. **v1's "sites" are not places.** EpiCollect field 1 holds `"<what3words> <INITIALS>"`,
   e.g. `"grace.reprints.jigsaw MG"`. v1 keeps only the initials and treats them as the
   site. `MG` covers four different points on the river (positions 11, 12, 15 and 16),
   averaged together and pinned to one invented coordinate. Ten other codes do the same.
4. **v1's cleaning corrupted readings.** `clean.py` turns prose into numbers
   (`"cloudy"` → 30 NTU); `clean_data.py` divides suspicious values by 10 and overwrites
   the original; `llm_cleanup/` asks a language model to "fix" outliers.

## Layout

```
Dashboard/
  frontend/            v1 — untouched
  frontend-v2/         v2 React app, built with base '/'
  backend/
    main.py            v1 — untouched, zero diff
    main_v2.py         imports the v1 app and mounts /api/v2 on it
    coln_v2.db         v2's own database (gitignored; rebuildable)
    v2/
      ingest.py        fetch from EpiCollect -> raw_entries -> derived tables
      cleaning.py      one raw value -> one measurement, non-destructively
      locations.py     what3words -> a place on the river
      db.py            schema
      wfd.py           bands + the plain-English wording used everywhere
      insights.py      every statistic (the LLM never does arithmetic)
      api.py           data endpoints
      facts.py         the facts pack a report is written from
      llm.py           provider client (mistral | anthropic | stub)
      prompts.py       system + user prompts
      schemas.py       report JSON schema + validator
      verify.py        checks the written report against the facts pack
      engine.py        facts -> LLM -> validate -> verify -> store
      render.py        report -> markdown / printable HTML
      reports_api.py   report endpoints + job queue
      scheduler.py     writes the report for any finished round
  deploy/*.example     nginx and systemd, as examples — not applied
```

away and rebuilt.

### Cleaning rules

The principle: **transform the representation, never the measurement.** `value_raw` is
always kept. Nothing is rescaled. Every transformation writes a `cleaning_log` row.

| Input | Result |
|---|---|
| `0.07ppm`, `50 ppm`, `30 NTU` | unit stripped; ppm treated as mg/L (true for dilute freshwater) |
| `0,11` | comma → decimal point |
| `O.06`, `O.oo`, `..01` | letter O → zero, doubled decimal point fixed |
| `150mm`, `0.5m`, `1 inch`, `2.6ft` | converted to cm |
| `10-25` | test-strip band: bounds kept, midpoint as the value |
| `10-25 (20)` | the volunteer's own figure wins; band kept as bounds |
| `<0.02`, `﹤25` | the bound itself, marked below-detection — never halved |
| `Nil` | zero, marked as reported in words |
| `Clear`, `Cloudy`, `Muddy` | an ordered category. **No number is assigned.** |
| `Low`, `In spate` in the turbidity field | a note about flow, not clarity — off the scale |
| numeric but implausible | kept, marked unusable, queued for a decision. Never divided by 10. |

### Turbidity is not a number

388 of 416 turbidity readings are words. Volunteers judge it by eye, so v2 records it on an
ordered scale (`crystal_clear` … `muddy`) with `value` left NULL. It is never averaged and
never graded against the WFD NTU bands, which are meter thresholds. Water depth has the
same treatment for its 43 verbal readings.

Consequence: `usable = 1` does **not** imply `value IS NOT NULL`. Any query doing arithmetic
needs `AND value IS NOT NULL` as well, or ordinal rows poison the result.

### The review queue

25 readings could not be interpreted with confidence. Nothing was guessed and nothing was
dropped: each sits in `review_queue` with a suggested reading that is **displayed, never
applied**. Accepting one writes to `manual_corrections`, which survives a rebuild and is
applied after automatic cleaning — the only route by which a human judgement enters the
data, and reversible by deleting the row.

The queue currently holds the two possible-duplicate locations, four dissolved-oxygen zeros,
four implausible chemical values with suggested decimal-point corrections
(`phosphate 47` → `0.47`), and about a dozen genuinely unreadable entries.

## Locations

A location is a what3words point, not a person's initials. `river_order` (from
`LocationReferenceTable.xlsx`, `MY_ID`) orders every "along the river" view source to Thames.
Volunteer initials are kept as `observations.recorder` — who collected the sample, never
where.

`river_order` is a **float**. Four points missing from the reference spreadsheet were located
from the public what3words service and placed by projecting onto the reference polyline,
giving fractional positions (15.98, 38.92, 43.50, 46.77) that sort correctly between the
integer `MY_ID`s. Sort on it numerically; never display it — "point 38.92 on the river" is
not a thing to show anyone. `locations.source` distinguishes `reference_table` from
`supplement` so that provenance stays visible.

Two of those four sit within ~30 m of an existing point and may be duplicates. They are kept
separate pending a decision in the review queue.

## The georeferenced backup

Positions no longer depend on a volunteer typing a what3words address correctly. The owner's
second EpiCollect project, **CRG backup data with georef** (`crg-backup-data-with-georef`),
carries the same fieldwork with a real lat/long on every entry and the readings tidied into
numbers. Where the two datasets disagree, that one wins.

    python -m backend.v2.crg_georef --fetch     # fetch it and merge
    python backend/v2/ingest.py --refresh       # rebuild, then merge again

`v2/crg_georef.py` runs as a pass over the derived tables *after* `ingest.rebuild()`, because
a rebuild empties them; `--refresh` re-runs the merge on its own, and `--skip-crg` turns that
off. The backup payloads live in `crg_raw_entries` under the same never-mutate contract as
`raw_entries`. `observations.crg_status` says where each sample stands: `matched`,
`original_only` (the backup does not have it), `crg_only` (the original does not).

It is a second source, not a replacement. It has no dissolved oxygen, no conductivity, no
volunteer initials, no photos and no landowner, and it is missing 16 samples the original
has; all of those still come from the original. 39 of its 512 rows repeat a sibling exactly
and are dropped, which is why the August 2026 round is 28 samples and not 51.

`data/crg_locations.csv` is the sampling-point table it produces: one row per distinct
coordinate, every one confirmed against the what3words service. It supersedes the four
supplement points for coordinates while keeping their `river_order`.

### What the backup does not get to overwrite

**The owner's own decisions.** Anything in `review_decisions` or `manual_corrections` is left
exactly as it is — 16 readings and 2 location merges. Someone who has looked at a reading and
said "that 23 is a mistyped 0.23", "that one was never measured", or "those two squares are
one spot on the bank" has better information than a bulk dataset, and those decisions are
meant to survive every rebuild. A merged-away square is never recreated as a location and its
samples land on the square the owner kept.

**A missing reading, with a zero.** The backup stores a plain `0` where a volunteer wrote
that no reading was taken — "No water", "Tributary dry", "Insufficient kit to test", "NA",
"Invalid" — and where the original field was blank. Adopting those would put 65 false zeros
into phosphate, ammonia and nitrate and pull every average down, which is the fault that made
the v1 numbers untrustworthy.

So a zero counts as a reading of zero only when the original was also a number or a plain nil
("Nil", "0.00 ppm", "O.00"). Otherwise `write_not_measured()` records that nothing was
measured, in exactly the shape the owner's own "not measured" decision produces: every value
column NULL, `qualifier='absent'`, `usable=0`, `value_raw` keeping what the volunteer wrote.
**A missing reading is never stored as a number.** Everything that computes a figure filters
`usable = 1` and `o.excluded = 0`, so these cannot reach a mean, a band, a chart or the CSV
export; they stay visible on the data page with the volunteer's own words as the reason. Each
one is logged as `crg_zero_withheld`, and `CRG_TRUST_ZEROS=1` adopts them anyway.

### One visit submitted twice

A volunteer who spots a typo sometimes submits the whole visit again rather than editing it.
`exclude_re_records()` keeps the newest submission and excludes the rest, but only where the
readings are identical, so two volunteers who genuinely sampled the same bridge at the same
minute are left alone. The older record is excluded, never deleted: the raw entry is
untouched and `excluded=1` keeps it out of every figure while the reason stays attached. One
sample qualifies today, `arching.probably.stickler` on 7 February 2026.

## Reports

**The site's Reports page is a static PDF, not this engine.** `pages/Reports.jsx` embeds and
offers for download whichever report the owner has written and dropped into
`frontend-v2/public/reports/` — currently `coln-report-august-2026.pdf`. The LLM pipeline
below still exists, is still runnable from the backend, and is not deleted: it is just not
what a visitor to the site sees. Everything from here on describes that dormant engine.

**One kind of report: one per round of testing, covering the whole river.** Location,
comparison, trend, catchment and data-quality report types were built and then cut, along
with the parish-council and technical registers — their builders survive in `facts.py` and
in git history if they are ever wanted back.

How one is written:

1. `facts.py` builds a **facts pack** — every figure computed in Python, each with a stable
   id (`location|<w3w>|phosphate|mean`). It includes the whole-river summary for the round,
   the comparison with the previous round, category counts for word-only measures, and the
   **downstream profile** for phosphate, ammonia and nitrate, ordered source to Thames.
2. The model is given the facts pack and writes narrative **around** it, returning JSON
   matching `schemas.py`. It never does arithmetic.
3. `schemas.py` validates the JSON in Python. Mistral does not enforce a schema server-side,
   so this is load-bearing, not a safety net. One corrective retry on failure.
4. `verify.py` extracts every number from the narrative and checks it against the facts
   pack, checks every `evidence_id` exists, and checks the banned content: landowner names,
   health advice, and an invented numeric turbidity. On failure it retries once with the
   specific problems listed, then stores the result **with** its verification record.
5. The result is stored with its verification record either way — green when every figure
   matched, amber with the list when something did not. (The old Reports UI showed this
   badge; the current static-PDF page does not call this pipeline at all — see above.)

```bash
python -m v2.scheduler --dry-run   # what is due
python -m v2.scheduler             # write it
```

A round counts as finished 5 days after its last sample (`ROUND_SETTLE_DAYS`), since
volunteers submit over several days. The current data yields 14 reports; a second run
generates nothing.

### Provider

`REPORT_LLM_PROVIDER` selects `mistral` (default), `anthropic`, or `stub`.
`stub` returns schema-valid JSON with no network call, so the whole pipeline can be
exercised with no key and no cost — that is how it has been tested.

**Untested:** no real Mistral call has ever been made. There is no `MISTRAL_API_KEY` in the
development environment; it lives on the droplet. The prompts are unproven against the
actual model, and that is the largest remaining risk in this work.

## Deploying

**Done, 2026-09-17.** `www.colnrg.app` serves `frontend-v2/dist` at `/`; the backend runs
`main_v2:app` (v1's whole app imported into it, so `/api` and `/api/v2` are one process); v1's
own `frontend/dist` is still on disk on the droplet, untouched, just not what nginx's `root`
points at.

It was deployed straight from this Mac by copying files over SSH -- `backend/v2/`,
`main_v2.py`, `requirements.txt` and a checkpointed copy of `coln_v2.db` rsynced to the
droplet, `pip install`ed, then `frontend-v2/dist/` rsynced into place -- **not** via
`git pull` on the droplet, because this Mac's `git` cannot currently push to GitHub (SSH key
rejected; see git log for whether that's since been fixed). The droplet's own checkout is
still on `main` and does not have these commits; deploying again the same way is fine, but a
`git pull`-based deploy won't work until push access is sorted out.

`deploy/new-nginx.conf.example` and `deploy/coln-v2-reports.{service,timer}.example` are
examples for the pattern used; the live file is `/etc/nginx/sites-enabled/coln-dashboard` --
see `MIGRATION.md` for the cert and everything else infrastructure. The repo's
`deploy/nginx.conf` is HTTP-only and will not reproduce HTTPS.

Sketch of a re-deploy from this state:

```bash
# frontend
cd Dashboard/frontend-v2 && npm run build
rsync -e 'ssh -i SSH/coln-dashboard' -avz --delete dist/ \
  root@161.35.168.168:/opt/coln-dashboard/frontend-v2/dist/

# backend (only if v2/ changed)
rsync -e 'ssh -i SSH/coln-dashboard' -avz backend/v2/ \
  root@161.35.168.168:/opt/coln-dashboard/backend/v2/
ssh -i SSH/coln-dashboard root@161.35.168.168 'systemctl restart coln-api.service'
```

`POST /api/v2/reports/generate` and `POST /api/v2/review-queue/{id}` are gated behind
`ADMIN_API_KEY`, which **is** set in the droplet's `/etc/environment`, alongside
`MISTRAL_API_KEY` (verified 2026-09-17; neither has been exercised by a real request from the
site itself, since Reports is a static PDF -- see above).

### Known-fixed-in-passing while deploying

- `frontend-v2/src/components/LocationMap.jsx` was pulling map tiles straight from
  `tile.openstreetmap.org`, which the production CSP's `img-src` has never allowed (only
  `*.basemaps.cartocdn.com`, matching v1's map). Switched to the same CartoDB tiles v1 uses.
  CARTO itself now requires a free API key on those tiles (since August 2026) or shows an
  "API KEY REQUIRED" watermark; `VITE_CARTO_API_KEY` (see `.env.example`) switches to the
  keyed endpoint once set. **v1's own map has the same watermark and was not fixed** -- it is
  no longer deployed, and the owner asked not to spend more effort on it.
