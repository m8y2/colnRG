# Coln River Guardians — v2

v2 is a rebuild of the dashboard for people with no technical background, plus a reporting
engine that writes one report per round of testing. It lives beside v1, not on top of it:
v1 keeps `/` and its own database, v2 gets `/v2` and its own.

Everything here is on the `v2` branch. Nothing has been deployed.

## Why v2 exists

Two problems with v1:

1. **It was written for someone who already understood it.** "Phosphate 0.17 mg/L, WFD
   Moderate" means nothing to a volunteer, a parish councillor or a schoolchild.
2. **The reporting was a thin beta** — one prompt producing a wall of prose, with nothing
   stopping the model inventing figures.

Two more problems were found while building it, and they were the bigger ones:

3. **v1's "sites" are not places.** EpiCollect field 1 holds `"<what3words> <INITIALS>"`,
   e.g. `"grace.reprints.jigsaw MG"`. v1 keeps only the initials and treats them as the
   site. `MG` covers four different points on the river (positions 11, 12, 15 and 16),
   averaged together and pinned to one invented coordinate. Ten other codes do the same.
4. **v1's cleaning corrupted readings.** `clean.py` turns prose into numbers
   (`"cloudy"` → 30 NTU); `clean_data.py` divides suspicious values by 10 and overwrites
   the original; `llm_cleanup/` asks a language model to "fix" outliers.

## Layout

```

  frontend-v2/         v2 React app, built with base '/v2/'
  backend/
    main.py            v1 — untouched, zero diff

    coln_v2.db         v2's own database (gitignored; rebuildable)
    v2/
      ingest.py        fetch from EpiCollect -> raw_entries -> derived tables
      cleaning.py      one raw value -> one measurement, non-destructively
      locations.py     what3words -> a place on the river
      db.py            schema
      wfd.py           bands + the plain-English wording used everywhere
      insights.py      every statistic (the LLM never does arithmetic)
      api.py           data endpoints
      facts.py         the facts pack a report is written from
      llm.py           provider client (mistral | anthropic | stub)
      prompts.py       system + user prompts
      schemas.py       report JSON schema + validator
      verify.py        checks the written report against the facts pack
      engine.py        facts -> LLM -> validate -> verify -> store
      render.py        report -> markdown / printable HTML
      reports_api.py   report endpoints + job queue
      scheduler.py     writes the report for any finished round
  deploy/v2-*.example  nginx and systemd, as examples — not applied
```

## The data

### Cleaning rules

The principle: **transform the representation, never the measurement.** `value_raw` is
always kept. Nothing is rescaled. Every transformation writes a `cleaning_log` row.

| Input | Result |
|---|---|
| `0.07ppm`, `50 ppm`, `30 NTU` | unit stripped; ppm treated as mg/L (true for dilute freshwater) |
| `0,11` | comma → decimal point |
| `O.06`, `O.oo`, `..01` | letter O → zero, doubled decimal point fixed |
| `150mm`, `0.5m`, `1 inch`, `2.6ft` | converted to cm |
| `10-25` | test-strip band: bounds kept, midpoint as the value |
| `10-25 (20)` | the volunteer's own figure wins; band kept as bounds |
| `<0.02`, `﹤25` | the bound itself, marked below-detection — never halved |
| `Nil` | zero, marked as reported in words |
| `Clear`, `Cloudy`, `Muddy` | an ordered category. **No number is assigned.** |
| `Low`, `In spate` in the turbidity field | a note about flow, not clarity — off the scale |
| numeric but implausible | kept, marked unusable, queued for a decision. Never divided by 10. |

### Turbidity is not a number

388 of 416 turbidity readings are words. Volunteers judge it by eye, so v2 records it on an
ordered scale (`crystal_clear` … `muddy`) with `value` left NULL. It is never averaged and
never graded against the WFD NTU bands, which are meter thresholds. Water depth has the
same treatment for its 43 verbal readings.

Consequence: `usable = 1` does **not** imply `value IS NOT NULL`. Any query doing arithmetic
needs `AND value IS NOT NULL` as well, or ordinal rows poison the result.

### The review queue

25 readings could not be interpreted with confidence. Nothing was guessed and nothing was
dropped: each sits in `review_queue` with a suggested reading that is **displayed, never
applied**. Accepting one writes to `manual_corrections`, which survives a rebuild and is
applied after automatic cleaning — the only route by which a human judgement enters the
data, and reversible by deleting the row.

The queue currently holds the two possible-duplicate locations, four dissolved-oxygen zeros,
four implausible chemical values with suggested decimal-point corrections
(`phosphate 47` → `0.47`), and about a dozen genuinely unreadable entries.

## Locations

A location is a what3words point, not a person's initials. `river_order` (from
`LocationReferenceTable.xlsx`, `MY_ID`) orders every "along the river" view source to Thames.
Volunteer initials are kept as `observations.recorder` — who collected the sample, never
where.

`river_order` is a **float**. Four points missing from the reference spreadsheet were located
from the public what3words service and placed by projecting onto the reference polyline,
giving fractional positions (15.98, 38.92, 43.50, 46.77) that sort correctly between the
integer `MY_ID`s. Sort on it numerically; never display it — "point 38.92 on the river" is
not a thing to show anyone. `locations.source` distinguishes `reference_table` from
`supplement` so that provenance stays visible.

Two of those four sit within ~30 m of an existing point and may be duplicates. They are kept
separate pending a decision in the review queue.

## Reports

**One kind of report: one per round of testing, covering the whole river.** Location,
comparison, trend, catchment and data-quality report types were built and then cut, along
with the parish-council and technical registers — their builders survive in `facts.py` and
in git history if they are ever wanted back.

How one is written:

1. `facts.py` builds a **facts pack** — every figure computed in Python, each with a stable
   id (`location|<w3w>|phosphate|mean`). It includes the whole-river summary for the round,
   the comparison with the previous round, category counts for word-only measures, and the
   **downstream profile** for phosphate, ammonia and nitrate, ordered source to Thames.
2. The model is given the facts pack and writes narrative **around** it, returning JSON
   matching `schemas.py`. It never does arithmetic.
3. `schemas.py` validates the JSON in Python. Mistral does not enforce a schema server-side,
   so this is load-bearing, not a safety net. One corrective retry on failure.
4. `verify.py` extracts every number from the narrative and checks it against the facts
   pack, checks every `evidence_id` exists, and checks the banned content: landowner names,
   health advice, and an invented numeric turbidity. On failure it retries once with the
   specific problems listed, then stores the result **with** its verification record.
5. The UI shows an honest badge either way — green when every figure matched, amber with the
   list when something did not.

```bash
python -m v2.scheduler --dry-run   # what is due
python -m v2.scheduler             # write it
```

A round counts as finished 5 days after its last sample (`ROUND_SETTLE_DAYS`), since
volunteers submit over several days. The current data yields 14 reports; a second run
generates nothing.

### Provider

`REPORT_LLM_PROVIDER` selects `mistral` (default), `anthropic`, or `stub`.
`stub` returns schema-valid JSON with no network call, so the whole pipeline can be
exercised with no key and no cost — that is how it has been tested.

**Untested:** no real Mistral call has ever been made. There is no `MISTRAL_API_KEY` in the
development environment; it lives on the droplet. The prompts are unproven against the
actual model, and that is the largest remaining risk in this work.

## Deploying

Not done. `deploy/v2-nginx.conf.example` and `deploy/coln-v2-reports.{service,timer}.example`
are examples to merge into the live config, which is
`/etc/nginx/sites-enabled/coln-dashboard` — see `MIGRATION.md`, which supersedes everything
here on infrastructure. The repo's `deploy/nginx.conf` is HTTP-only and will not reproduce
HTTPS.

Sketch:

```bash
# frontend
cd Dashboard/frontend-v2 && npm run build
rsync -e 'ssh -i ~/.ssh/id_ed25519' -avz dist/ \
  root@161.35.168.168:/opt/coln-dashboard/frontend-v2/dist/

# backend: switch the service to main_v2:app, then
ssh root@161.35.168.168 'cd /opt/coln-dashboard && git checkout v2 && git pull \
  && cd backend && python -m v2.ingest --fetch \
  && systemctl restart coln-api.service'
```

`POST /api/v2/reports/generate` and `POST /api/v2/review-queue/{id}` are gated behind
`ADMIN_API_KEY` when that variable is set, and open when it is not so local development
works. **Set it in production**, or anonymous traffic can spend the project's API credit.

## Known v1 bugs, deliberately not fixed

- Both bar charts on the live site draw axes and no bars — "Long-term Site Averages" and
  "Round by round results". Two of seven tabs show nothing.
- `backend/main.py` uses `datetime.now(timezone.utc)` in `/api/health` and the admin key
  endpoint but never imports `timezone` — a `NameError` waiting to happen.
- `backend/AGENTS.md` still documents Ollama-on-a-droplet report generation; that moved to
  the Mistral API in commit `5902e0e`.
- v1's `dashboard.db` has drifted from source (376 rows locally, 475 live, 489 in
  EpiCollect) and is partly overwritten by the old cleaning. It is not a reference for
  anything now.
